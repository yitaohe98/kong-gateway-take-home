# 工程决策日志

本文档界定分布式限流任务的方案边界：哪些部分经过了重点设计，哪些部分进行
了有意简化，以及服务达到生产就绪状态前还需要补齐哪些能力。

## 架构

```text
                                  准入请求
客户端 ----> 可信网关 -----------------------------+
                  |                                |
                  |                       +--------v--------+
                  |                       |    负载均衡器    |  可选
                  |                       +--------+--------+
                  |                                |
                  |                  +-------------+-------------+
                  |                  |             |             |
                  |              限流器 1       限流器 2       限流器 3
                  |                  \             |             /
                  |                   +------------+------------+
                  |                                |
                  |                          Redis Primary
                  |                                |
                  |                         生产环境副本
                  |
                  +---- 允许 ----> 上游服务
                  +---- 拒绝 ----> 向客户端返回 429

运维方/控制平面 ---- PUT /v1/config ----> 任意限流器副本
```

网关会在转发业务请求前调用 Admission API。限流器副本不保存权威配额状态，
而是通过同一个 Redis Primary 共享配置和 Bucket。当前 Compose 演示实现了
三个限流器和一个 Redis Primary，但没有实现图中作为生产扩展项展示的可选
负载均衡器和 Redis 副本。

## 重点实现的部分

- **准入正确性：** Path、Client ID 和 IP 作为一个 all-or-nothing 决策进行
  判断；被拒绝的流量不消耗配额。
- **分布式一致性：** 所有副本共享一个权威配额池，避免单机内存限流导致的
  配额拆分。
- **Token Bucket 精度：** 使用统一的 Redis 时间源、整数 microtoken 和保留
  余数进行补充计算。
- **故障语义：** 无法确认 Redis 结果时，以 fail-closed 方式返回 `503`；
  确定配额耗尽时返回 `429` 和 `Retry-After`。
- **策略生命周期：** 安全初始化配置；更新时创建新 generation；不活跃
  Bucket 自动过期；配置值具有明确边界。
- **验证：** 单元测试和集成测试覆盖共享配额、原子扣减、策略重置、输入校验、
  重试等待时间和 Redis 故障。

## 有意简化的部分

- 交付物是独立的准入服务，而不是 Kong PDK 插件或内联反向代理。
- 一个全局策略包含三个强制维度；不支持可选维度、加权请求和多个命名策略。
- 每个请求固定消耗一个 Token；策略更新会重置有效 Bucket，而不会迁移状态。
- 服务信任内部网关提供的规范化身份信息，不校验 API Key、授权策略或 mTLS
  身份。
- 演示环境使用一个 Redis Primary 和简单 JSON 接口；完整的网关、控制平面
  与上游集成不属于本 MVP 范围。

## 达到生产就绪仍需补齐的能力

- **Redis 可用性：** 使用 Redis 副本配合 Sentinel 或托管故障转移；Primary
  切换后重新连接客户端；接受或解决异步故障转移可能丢失近期更新的问题。
- **安全：** 对调用方进行身份认证；为配置写入使用独立的高权限凭据；增加
  传输加密、密钥轮换和网络访问限制。
- **集成契约：** 定义带版本的 API 或 Gateway Adapter，明确超时、重试、
  身份和错误语义；增加覆盖 Gateway、Limiter、Redis 和上游服务的端到端测试。
- **结果不明确时的重试：** 增加请求幂等性，使调用方在响应丢失、配额可能
  已被扣除的情况下仍能安全重试。
- **可观测性：** 增加指标、链路追踪、仪表盘、告警、审计日志，以及符合
  生产流量特征的容量和负载测试。
- **运维：** 提供自动发布和回滚、配置变更控制、备份恢复流程，以及多主机
  故障测试。
- **突破单 Primary 的扩展能力：** 如果一个 Redis Primary 成为瓶颈，需要
  定义分区模型，或采用能够保留跨维度一致性要求的协调方案。

## 按重要性排序的工程决策

以下决策按照架构重要性由高到低排列，最后是更具体的实现决策。

## ED-001：All-or-nothing 准入

只有 Path、Client ID 和 IP 三个维度都允许时，请求才会被放行。被拒绝的请求
不会消耗任何配额。

## ED-002：集中协调配额

所有限流器副本共享一个 Redis 配额池，因此 Redis Primary 是单点故障。
生产环境应使用 Redis 副本配合 Sentinel 或托管故障转移，使客户端在 Primary
故障后重新连接到晋升的副本。异步故障转移仍可能丢失近期已确认的配额更新。

## ED-003：配额状态不确定时 fail closed

当 Redis 不可用、超时或无法返回可信结果时，服务返回 `503`。如果无法验证
配额，服务绝不会放行请求。

## ED-004：通过 limit 和 window 推导 Token Bucket 行为

每个维度只暴露 `limit` 和 `window_seconds`。Bucket 容量和最大突发量等于
`limit`，Token 以 `limit / window_seconds` 的速率补充；每个请求固定消耗
一个 Token。

## ED-005：使用 Redis 作为时间权威

所有副本使用 Redis Primary 时间，避免主机时钟差异。另一种方案是信任上游
时间戳，但这要求时钟事先完成对齐，而且调用方时间会影响配额状态，因此没有
采用。实现使用整数 microtoken 保留补充精度。

## ED-006：策略更新时重置配额

每次成功更新策略都会创建新的 generation 和全新 Bucket。这样可以保持更新
语义简单、可预测，但会重置已有配额。

## ED-007：信任网关提供的身份信息

MVP 信任内部网关提供的 Path、Client ID 和源 IP。生产部署应增加调用方身份
认证和授权。

## ED-008：保持 MVP 集成接口简单

MVP 提供小型独立准入与配置 API，不实现完整的网关或上游集成。生产环境应
定义带版本的标准契约，并增加覆盖网关、限流器、Redis 和上游服务的端到端
测试。

## ED-009：使用 Rust 和 Redis

Rust 具有较低的内存开销、可预测的性能、内存安全性和简单的原生部署方式。
Redis 提供快速共享状态、原子更新、自动过期，以及跨副本统一的时间源。

## ED-010：仅初始化配置一次

第一个启动的副本只会在配置不存在时创建默认策略。并发启动不会互相覆盖，
后续重启也会保留已有策略。

## ED-011：校验请求结构

无效请求包括缺少必填字段、JSON 类型错误、值为空或过长、IP 地址格式错误，
以及出现未知字段。它们会直接返回 `400`，不会检查或消耗配额。

## ED-012：按照最慢恢复的限制维度返回重试时间

当多个维度同时拒绝请求时，响应会列出全部限制维度，并将 `Retry-After`
设置为最长等待时间，避免在任一配额尚未恢复时建议调用方重试。

## ED-013：使不活跃 Bucket 过期

Bucket 在两个补充窗口内没有活动后过期，从而限制 Redis 内存使用。活跃
Bucket 每次被评估时都会刷新过期时间。

## ED-014：限制策略取值范围

`limit` 的取值范围为 `1`–`1,000,000`，`window_seconds` 的取值范围为
`1`–`86,400`。这些边界能够拒绝无效或极端策略，并保持补充运算可预测。
